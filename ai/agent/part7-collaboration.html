#第 9 章 协作模式：多个 Agent，如何分工、沟通、共存

"多 Agent 的力量不在于单体有多聪明，而在于如何分工协作。协作模式解决的是：N 个 Agent 组成团队时，谁说了算、谁做什么、信息怎么流动、冲突怎么处理。"

2023 年 3 月 14 日 OpenAI 发布 GPT-4。就在当天，一位研究员发了一条推文："如果我们让多个 GPT-4 实例相互对话，又会发生什么呢？"48 小时后，AutoGPT 诞生了。紧随其后，BabyAGI、AgentGPT、SuperAGI 等项目如雨后春笋般涌现——人们突然意识到：真正的力量并不在于单体 Agent 有多聪明，而在于多个 Agent 如何协同工作。

本章拆解四种协作模式，它们按集中程度从高到低排列：

#9.1 辩论模式（Debate）：两个大脑 + 一个裁判

#9.1.1 核心结构

三个角色：

  • Debater A：站在立场 A（比如"用协同过滤"），输出最强论据
  • Debater B：站在立场 B（比如"用内容过滤"），输出最强论据
  • Judge：独立评估双方，输出最终结论（选边 / 投票 / 综合出第三种方案）

#9.1.2 适用场景

场景辩论双方Judge价值
技术选型"微服务 vs 单体"架构师 Agent避免"一家之言"的 bias
策略权衡"激进增长 vs 稳健盈利"战略顾问 Agent多视角分析
代码审查"这段代码应该重构 vs 应该保持原样"Reviewer Agent减少盲点
安全审计"这个 API 有漏洞 vs 没问题"红队 Agent对抗式提高安全

#9.1.3 迭代辩论

基础辩论是"一次投一票"，迭代辩论是"辩论 N 轮，每轮对方看了上一轮论据后再辩"——效果显著更强，代价也更高：

轮数精准率提升成本增量
1基础1×
2+5-10%3×
5+15-20%10×

#9.1.4 关键设计决策

决策选项Trade-off
Judge 要不要和 Debater 是同一个模型是（经济） / 否（精准）同一个模型可能有相同的 bias，选另一个模型效果更好但成本翻倍
Debater 立场要不要预设预设（"你必须站 A"） / 让模型自己选预设能保证覆盖所有角度，自己选可能两边都选同一个
Judge 输出是选边还是综合选边（简单） / 综合（高价值）综合能力更强但 Judge 难度更大

#9.2 委托模式（Delegate）：Manager → Specialist 的层级组织

#9.2.1 核心结构

这是半集中式的协作——Manager 负责任务分解 + 结果汇总，每个 Specialist 专注于单一职责。

#9.2.2 两个工程实现范式

范式机制代表
静态角色分工在 Prompt 里硬编码 Manager/Specialist 的角色、能力边界、对话模板CrewAI 的 Role-Based 架构、AutoGen 初始化时指定角色
动态 SupervisionSupervisor Agent 每次都从"员工池"里挑最合适的 Specialist + 动态拆任务LangGraph Supervisor 模式、AutoGen GroupChat

#9.2.3 三个工程挑战

挑战症状对策
信息孤岛Researcher 发现了竞品 A 的 bug，但 Coder 完全不知道Manager 在传任务时注入必要背景，不要只传裸任务
角色模糊Coder 有时也想做设计，Designer 也想改代码在 Prompt 里明确角色边界 + 强制"超出职责就说不会"
Manager 瓶颈Manager 变成新的单点瓶颈可以让 Manager 也委托——形成两层甚至三层 Manager

#9.2.4 工业代表框架

框架角色分工方式灵活度
CrewAIRole-Based：先定义角色、目标、工具，再 Crew().kickoff()低-中
AutoGen对话式：Agent 之间通过对话协商分工高
LangGraphSupervisor 图：显式声明 Manager → Specialist 的图结构高

#9.3 路由模式（Router）：进来一个请求，先路由再分发

#9.3.1 核心结构

#9.3.2 分类 vs 路由

很多人把 Router 和 Manager 搞混，核心区别是：

  • Manager 收到一个大任务，拆成多个子任务，分发给多个 Specialist；
  • Router 收到一个请求，先分类，路由到最合适的 Specialist（通常只需要一个）。
维度路由委托
输入一个请求一个目标
输出选出 N 个 Agent（通常 1 个）拆出 N 个子任务 + 分发给 N 个 Agent
典型场景多领域客服、多 Agent API 网关全栈项目、端到端任务

#9.3.3 路由分类的三种实现

方法精准率成本代表
规则路由（if-else）高（在规则覆盖范围内）极低关键词匹配、正则
Embedding 相似度路由中-高低（只跑一次 embedding）把每个 Specialist 的能力描述 embedding，请求向量做相似度匹配
LLM 路由最高中（一次 LLM 调用）让 LLM 读请求 + 读所有 Specialist 描述，输出"选哪个"

#9.3.4 工业案例：企业级客服网关

Router Agent (LLM 路由): 请求: "我的订单 12345 为什么还没发货？" → 匹配 "订单状态 Specialist" → 路由 请求: "我想退订会员" → 匹配 "退款 Specialist" → 路由 请求: "刚才收到诈骗短信，请问是不是你们发的？" → 匹配 "安全 Specialist" + "升级到人工客服"

#9.4 群体模式（Swarm）：去中心化的涌现式协作

#9.4.1 核心结构

群体模式是去中心化的——没有 Manager、没有 Router。每个 Agent 只遵循简单规则，通过广播/订阅/消息队列与邻居交互，最终涌现出复杂的整体行为。

#9.4.2 三种涌现机制

机制启发自工业代表说明
蚁群算法（ACO）蚂蚁信息素网络路由优化每个 Agent 只看信息素浓度，走浓度高的路径——全局涌现出最优网络路由
粒子群（PSO）鸟群飞翔参数调优、路径规划每个 Agent 记住自己的历史最优 + 全局最优，综合两个信息调整位置
黑板系统（Blackboard）早期 AI（1970s）AutoGPT（早期形态）所有 Agent 共享一个"黑板"——谁都可以读谁都可以写，通过黑板上的信息自然分工

#9.4.3 与 9.1-9.3 的对比

模式去中心化程度可控性精准率适用场景
辩论低高高事实争议、策略权衡
委托中高高明确的多角色任务
路由中高中多领域客服
群体最高低未知（风险高）探索型、不需要精确控制的场景

#9.4.4 关键风险：不可控性

群体模式最大的风险是涌现行为不可控——你可能得到一个远超单体 Agent 的"集体智慧"，也可能得到一个集体幻觉或混沌振荡的"集体疯狂"。

治理手段：

  • 给每个 Agent 设预算/能量上限（防止无限循环）；
  • 用全局 Governor Agent 监控整体行为异常；
  • 给反馈信号（如 Meta 反思记忆），让失败的涌现模式沉淀成"不要再这么做"的经验。

#后记：熵的园丁

熵是生命的敌人，但也是进化的朋友。系统越复杂，熵越高，但熵的每一次峰值，都是下一次创新的起点。

黄佳在全书最后一章提出一个关键隐喻：

软件工程师曾经是精密钟表的制造者——目标是消除不确定性、消灭熵、打造永恒运转的确定性系统。

软件工程师现在是熵的园丁——我们不再试图消灭不确定性，而是在不确定性中建立秩序；不再试图控制系统的每一个齿轮，而是设计让系统自我演化的生态。

Agent 时代的工程师角色从"控制者"变为"园丁"：

  • 感知模式给 Agent 装上了"眼睛"；
  • 记忆模式给 Agent 装上了"脑子"；
  • 推理模式给 Agent 装上了"思考方法"；
  • 行动模式给 Agent 装上了"手和脚"；
  • 反思模式给 Agent 装上了"学习能力"；
  • 协作模式给 Agent 装上了"社会能力"。

这六大模式族，就是 Agent 时代工程师的新工具箱——一个从代码组织进化到意图、记忆、行动与协作组织的工具箱。
