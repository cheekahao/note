#AI编码工具

#0. 导读与速览

三者都旨在「让 AI 编码更可控」，但控制的环节、规格的形态、约束的强度、执行权的归属完全不同。用本体视角看，它们是同一条「意图→规范→产物→证据」链路上的不同实现（详见第 1 章）。

维度OpenSpecSuperpowersOuroboros
一句话定位给 AI 编码助手加一层规格层：先写清楚"要做什么"再动手给 AI 编码 Agent 套一套软件开发方法论：TDD + 子代理 + 不可跳过的流程Spec-first 的 Agent OS：访谈澄清 → 冻结规范 → 派给现有 agent 执行 → 自动验收 → 进化
核心关注需求/变更的规格与审计（why & what）代码的质量与纪律（how well）从模糊想法到验收通过的全自动闭环
规格形态可变增量 spec（Git Markdown，source of truth）一次性设计/计划文档（commit 入库，非规范性 spec）不可变 Seed（冻结 Pydantic model）+ EventStore
谁写代码你的 AI 工具（Claude/Cursor…）按 tasks 实现agent 自己（TDD + 子代理）你的现有 agent（14 种 runtime）按 AC 执行
约束强度轻（无固定阶段门，可随时改产物）强（HARD-GATE + hook；但提示层、用户指令可覆盖）强（ambiguity gate + 三阶段评估；含可选执行沙箱）
典型命令/触发/openspec-propose、/openspec-apply-change自然语言触发（如 "Let's build a ..."）ooo interview、ooo auto、ouroboros run
跨工具支持30+ 种 AI 工具10+ 种 harness14 种 runtime 后端
主语言/形态TypeScript 单 CLI（无需 Node 的独立二进制）Markdown skills + hooks（插件）Python CLI / MCP Server / TUI
适合谁存量项目改造、需要变更审计的团队在意 TDD 与代码审查质量的开发者想要"一句话到可验收交付"的自动化玩家

选型直觉：

  • 想解决"AI 老做偏、需求活在聊天记录里" → OpenSpec
  • 想解决"AI 写的代码质量差、不写测试" → Superpowers
  • 想要"给个模糊需求，它自己问清楚、做完、验收" → Ouroboros
  • 可组合，但需明确主流程归属——见第 5.2 节（苏格拉底 review 修正后补充）。

#1. 领域本体：统一解释三者的底层模型

#1.1 为什么用本体视角

本体（Ontology）在知识工程里指：对某一领域概念体系的显式、形式化说明，包含类（实体）、属性、关系、公理（不变量）与实例。用在这里的价值：

  1. 去营销噪声：三个工具各自宣称"规格层 / 方法论 / Agent OS"，本体提供统一标尺，让它们可比。
  2. 暴露真正的分歧点：例如"规格是否不可变""谁持有执行权"——这些才是选型关键，而不是 star 数。
  3. 指导组合：知道各工具覆盖了链路的哪些环节，才知道它们能否拼起来、接缝在哪。

#1.2 核心实体（类）

实体符号定义关键属性
意图Intent用户原始的、模糊的、未结构化的需求清晰度 clarity、歧义度 ambiguity
规格Specification对意图的明确化、可验证的陈述（what/why）可变性 mutability、粒度、是否 source of truth
计划Plan从规格到执行步骤的分解（how）任务粒度、依赖顺序
任务Task计划的最小可执行单元可勾选、可验证、上下文隔离
产物Artifact执行产生的东西：代码、文档、提交可追溯、可回滚
证据Evidence证明产物满足规格的凭据：测试、审查、评估结果可信度、成本、是否可被授予接受
验证Verification对照规格检查产物的过程阶段（机械/语义/共识）、门槛

#1.4 公理（不变量）

这五条是从三者设计中抽出的"应当成立的规律"，也是 review 的判据：

  • A1 规格优先：任一被接受的产物必须存在对应规格，使 验证(产物, 规格) 可判定。违反即"做偏了"。
  • A2 证据必要：产物的接受必须以证据为前提；没有证据的"完成"只是声称。（Superpowers 的 "Evidence over claims"、Ouroboros 的 Mechanical 阶段均体现此条。）
  • A3 约束传导：约束的强制层级决定流程可被跳过的程度——提示层约束可被用户指令覆盖，环境层（沙箱/worktree）约束不可。
  • A4 状态连续：闭环的连续性由持久化状态保证；无状态则"中断即失忆"（故 OpenSpec 依赖 Git、Ouroboros 依赖 EventStore、Superpowers 依赖 ledger）。
  • A5 可变性守恒：规格的"不可变"需区分实例级与类型级——冻结单个实例并生成新实例（Ouroboros 进化）、原地增量修改（OpenSpec delta spec）、一次性文档不回写（Superpowers）是三种不同选择。

#1.6 本体视角下的本质差异

把上表浓缩成一句话：

  • OpenSpec 是"规格与状态"专家：强化 Specification（可变增量）+ State（Git 审计），把执行权留给外部工具，验证较弱。
  • Superpowers 是"执行与证据"专家：强化 Task（上下文隔离的子代理）+ Verification（TDD + 审查），规格只是一次性设计文档。
  • Ouroboros 是"全链路闭环"实现：从 Intent 澄清到 Specification 冻结、执行委托、三阶段 Verification、再到 State 重放与进化，覆盖所有实体。

由此得出一个功能性结论（也是第 5 章组合建议的依据）：三者覆盖的环节互补但不完全正交——OpenSpec 与 Superpowers 在"谁主导 Specification/Plan"上会重叠，故组合时必须划清主流程归属。

#2. OpenSpec —— 规格驱动开发（SDD）的轻量规格层

#2.1 定位与理念

OpenSpec 在写代码之前，先让人类与 AI 就"要构建什么"达成一致（agree before you build），把规格和代码放进同一个 Git 仓库一起演进。官方理念原文：

→ fluid not rigid 流动而非僵化 → iterative not waterfall 迭代而非瀑布 → easy not complex 简单而非复杂 → built for brownfield not just greenfield 面向存量项目，不只是全新项目 → scalable from personal projects to enterprises 从个人项目扩展到企业级

它把"系统当前真实规格"（openspec/specs/）与"提议中的变更"（openspec/changes/）分开，因此特别适合存量项目改造与变更审计。

#2.2 安装与初始化

2curl -fsSL https://openspec.dev/cli/install.sh | sh

#2.3 核心工作流：五步闭环

步骤调用做什么产出
Explore/openspec-explore 或自然语言读代码、提问、权衡方案，不写代码对话中的结论
Propose/openspec-propose add-dark-modeAI 起草变更计划，停在计划changes/<name>/ 下 4 类产物
Review人工读按 proposal.md → specs/（最有价值）→ tasks.md 顺序审，直接改 Markdown修订后的计划
Apply/openspec-apply-change（建议新会话）AI 逐条勾选 tasks.md 实现；中断后重开会从第一个未勾选项续代码 + 勾选完的 tasks
Archive/openspec-archive-change把 delta spec 合并进 specs/，变更目录移入 changes/archive/<日期>-<name>/更新后的主规格

#2.4 目录结构与产物格式

1openspec/
2├── config.yaml          # 项目设置与 AI 上下文/规则
3├── specs/               # 系统当前真实规格（source of truth）
4└── changes/             # 进行中的变更
5    └── archive/         # 已完成的变更，如 2026-11-19-add-dark-mode/
6        ├── proposal.md
7        ├── design.md
8        ├── tasks.md            # 所有 checkbox 已勾选
9        ├── .openspec.yaml      # 变更元数据（goal / skip_specs 等）
10        └── specs/rate-limiting/spec.md   # delta spec

四类产物要点（spec-driven schema）：

  • proposal.md：1–2 页，聚焦 why 而非 how。含 ## Why / ## What Changes / ## Capabilities / ## Impact。纯重构/文档类无 capability 时需在 .openspec.yaml 设 skip_specs: true。
  • specs/<capability>/spec.md（delta spec）：用 ## ADDED / MODIFIED / REMOVED / RENAMED Requirements 表达增量。
    • 场景标题必须正好 4 个 #：#### Scenario: xxx（3 个会静默失败！）
    • 每个 requirement ≥ 1 个 scenario，场景须含 WHEN/GIVEN + THEN；规范性需求用 SHALL/MUST。
    • MODIFIED 必须写完整更新后内容（不能只写片段）；REMOVED 须含 **Reason** 与 **Migration**。
  • design.md：## Context / ## Goals / Non-Goals / ## Decisions / ## Risks / Trade-offs / ## Migration Plan / ## Open Questions。
  • tasks.md：- [ ] 1.1 ... 勾选格式；每个任务写明"如何验证完成"；归档等后续动作用普通 bullet（不参与勾选）。

delta spec 示例（README 原文）：

1## ADDED Requirements
2### Requirement: Theme selection
3The app SHALL let users switch between light and dark themes,
4defaulting to the system preference.
5
6#### Scenario: User toggles dark mode
7- **WHEN** the user clicks the theme toggle
8- **THEN** the app switches to dark mode and persists the choice

#2.5 完整示例：从零到归档（dark mode）

常用 CLI：openspec list / show <name> / view / validate --all / status --change <id> / instructions proposal --change <id> / doctor。

#2.6 配置与自定义

openspec/config.yaml（字段 schema 必填；context/rules/operations 追加指令，不改产物结构）：

1schema: spec-driven
2context: |
3  Designs and tasks must cover Windows, macOS, and Linux
4  Write all artifacts in Chinese
5rules:
6  proposal:
7    - Keep proposals under 500 words
8    - Always state what is out of scope
9  tasks:
10    - Break tasks into chunks of max 2 hours
11operations:
12  apply:
13    guidance:
14      - Keep test summaries concise
  • 语言适配：在 context 写 Write all artifacts in Chinese. 即可让所有产物用中文。
  • 不要改内置 skill 目录（openspec update 会整目录覆盖）；定制放 context/rules，或自建同名之外的 skill（如 .agents/skills/team-propose/）。
  • 工作流 profile：openspec config profile（12 种，core 默认 6 个）→ openspec update 生效。

验证安装：openspec --version；openspec view 看 dashboard；openspec doctor 体检。

#3. Superpowers —— 给 AI 编码 Agent 的「软件开发方法论」

#3.1 定位与哲学

官方定义："a complete software development methodology for your coding agents, built on top of a set of composable skills and some initial instructions that make sure your agent uses them."

它不是 CLI，也不是"更聪明的提示词"，而是一组可组合的 Markdown skills + 一段启动引导（bootstrap），安装后强制 agent 按工程纪律工作。核心是把 agent 当作"已批准计划的执行者"：你说"做个东西"，它不会直接写代码，而是先退一步问你到底想解决什么问题。

四条哲学：

  • Test-Driven Development —— 永远先写测试
  • Systematic over ad-hoc —— 流程胜过猜测
  • Complexity reduction —— 简单是首要目标
  • Evidence over claims —— 宣称完成前先取证

TDD 铁律：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST（先写实现？删掉重来）。

④ 执行计划subagent-driven-development（最彻底）/ executing-plans（最便宜）前者每任务派全新 implementer + reviewer 子代理（spec compliance + code quality 双 verdict）；后者同会话内实现、最后一次全分支审查
⑤ test-driven-developmentTDDRED → Verify RED → GREEN → Verify GREEN（跑项目完整测试套件） → REFACTOR
⑥ requesting-code-review请求审查派专门 reviewer 子代理，对照 plan 按严重程度报告；Critical 阻塞。配套 receiving-code-review 规定如何验证式响应
⑦ finishing-a-development-branch收尾跑完整测试 → 检测环境 → 三选一菜单（本地 merge / push+PR / 保留分支）→ 清理 worktree

subagent-driven-development 的关键机制：每个子代理都是全新 context（"第 50 个任务与第 1 个任务得到同样多的关注"，避免 context rot）；用 scripts/task-brief 生成唯一任务简报，永远不让子代理读整个 plan；用 ledger（progress.md）对抗上下文压缩后的重复派发。

#3.5 具体怎么用：从一句话到合并分支

当前版本靠自动触发，无需记斜杠命令。官方认可的完整触发句：

#3.6 底层机制（为何"不可跳过"）

  • Lazy loading：只有 bootstrap 在会话开始时注入（约 2K tokens），其余 skills 按需用 Skill 工具读取，保持初始上下文轻量。
  • SessionStart hook：插件注册 hook（matcher startup|clear|compact），把 using-superpowers/SKILL.md 全文包进 <EXTREMELY_IMPORTANT> 注入；因为含 compact，上下文压缩后也会重新注入。hook 本身不发网络请求。
  • 优先级：用户显式指令 / CLAUDE.md > skills > 默认行为。所以"不可跳过"并非绝对——你直接明说就能覆盖（见第 6 章 Q3 修订）。
  • 三重强制：hook 注入极端措辞（"if a skill applies, you MUST use it, not negotiable"）+ skill 内 <HARD-GATE> 与"常见借口表" + 作者用子代理压力测试持续加固（借鉴 Cialdini《影响力》的说服原则）。
  • 限制：这是提示层强制，不是沙箱/形式化保证；第三方评价为 "Compliance is tested, not guaranteed"。遥测默认开启，可用 export SUPERPOWERS_DISABLE_TELEMETRY=1 关闭。

#4. Ouroboros —— Spec-first 的 Agent OS（Q00/ouroboros）

#4.1 定位与核心概念

一句话：它不直接写代码，先通过苏格拉底式提问把模糊需求澄清成一份不可变规范（Seed），把规范交给用户已有的编码 agent 执行，再按验收标准自动核验。口号："Ask first, build second, check always." / "It gets smarter on its own. We just hold the line."

核心循环（衔尾蛇结构）：

关键概念：

概念说明
Seed访谈答案结晶出的不可变规范（frozen Pydantic model）：goal / ontology / acceptance criteria (AC) / constraints
Ambiguity gateAmbiguity = 1 - Σ(clarity_i × weight_i)，阈值 ≤ 0.2 才准生成 Seed（可 force 越过）
三阶段评估Mechanical（lint/build/test，$0，唯一能授予 acceptance）→ Semantic（$$）→ Multi-Model Consensus（$$$）
PAL Router模型分级 frugal(1x) → standard(10x) → frontier(30x)，失败升级、不自动降级
Event Sourcing所有状态变更 append-only 写入 SQLite，支持 replay / checkpoint / session 恢复
收敛ontology similarity ≥ 0.95 或 30 代上限时停止

本体澄清（见 A5）：Seed 的"不可变"是实例级的——单次执行中冻结，进化时生成新 Seed 实例，原实例不回写。

Agent OS 三层架构（跨 3 仓库）：Shell = Ouro-labs/ourocode（跨宿主 TUI）；Apps = Ouro-labs/ouroboros-plugins（插件契约）；OS = Q00/ouroboros（核心：Seed/Ledger/Runtime/MCP/安全边界）。内置 9 个重点 agent：Socratic Interviewer、Ontologist、Seed Architect、Evaluator、Contrarian、Hacker、Simplifier、Researcher、Architect。

⚠️ 与任何加密货币无关；另有一个不相关同名项目 razzant/ouroboros（自修改记忆 agent），别混淆。

#4.5 典型场景与注意点

  • 绿地项目全自动交付：ooo auto "..." —— 自动访谈、写 A 级 Seed、执行、验证。

  • 防"看起来对"的评估：Mechanical 检查 lint/build/test → Semantic 查 drift → 必要时多模型共识；ooo qa <artifact> 按自然语言质量门槛评估任意产物。

#5.2 组合建议（经苏格拉底 review 修订）

  • 规格 + 质量组合可落地，但必须划清主流程归属：OpenSpec 与 Superpowers 都想在同一个 agent 上定义"先做什么、按什么步骤做"——若同时启用两套 skill/workflow，会出现工作流竞争（两者都试图主导 Plan/阶段门）。可行分工是：
    • 用 OpenSpec 作为唯一 Spec/审计层（管 what & why，specs/changes 为 SoT）；
    • 用 Superpowers 仅在其 Apply 阶段接管执行纪律（TDD、子代理审查），并关闭/绕过 Superpowers 的 brainstorming 与 writing-plans，避免重复立项。
    • 这是社区常见搭配思路，但非官方组合，需自行验证兼容（第三方观点）。
  • 全自动交付：Ouroboros 自成闭环，适合"脑子里有个模糊想法、想让它自己问清楚做完并验收"的场景；代价是体系最重、配置项多、部分字段仍是占位。
  • 轻量起步：只想要"先写规格再写代码"这一个习惯，从 OpenSpec 的五步闭环入手成本最低；不要一上来三套全装。
  • 不要为了用工具而用工具：一次性脚本、探索性原型、明确的小修小补，直接写即可——公理 A1/A2 的价值随任务规模与协作人数递增。

#5.3 共同风险提示

  1. 核心约束大多在提示/流程层而非沙箱（Ouroboros 提供可选 exec_sandbox，Superpowers 用 worktree 做物理隔离，但都不是形式化验证的沙箱）；最终质量仍取决于模型能力与人的审查。
  2. 版本迭代快（尤其 OpenSpec v1→v2 命令大改），老教程容易过时，以实际安装版本的输出为准。
  3. 涉及"自动改代码、执行命令"的工具，在存量/生产项目上先读权限与沙箱配置，必要时开隔离 worktree。

#6. 苏格拉底式 Review：对本笔记自身的诘问

方法：用苏格拉底诘问法（elenchus）逐条检验笔记中的论断——先澄清概念，再追问隐含假设，再找反例，再推后果，最后检查证据来源。每轮给出「裁定」与「已落地的修订」，避免把 review 写成自说自话。

#Q1｜澄清："三者都让 AI 编码'更可控'"——"可控"指什么？

诘问：如果说 OpenSpec 控制的是"做对的事"，Superpowers 控制的是"把事做对"，Ouroboros 控制的是"从头到尾自动做对"——那"可控"是同一个概念吗？ 辨析：不是。按本体，OpenSpec 控制 Specification 的保真度，Superpowers 控制 Verification 的严格度，Ouroboros 控制整条链路的自动化程度。 裁定 + 修订：原表述过于笼统。已在第 0 章改为"控制的环节、规格的形态、约束的强度、执行权的归属完全不同"，并新增第 1 章本体来承载这一区分。✅

#Q2｜假设："三者可组合：OpenSpec + Superpowers"——组合真的无摩擦吗？

诘问：OpenSpec 的 Apply 用"你的 AI 工具按 tasks 实现"，Superpowers 则会强制同一 agent 先 brainstorming、再 writing-plans。两者同时启用，谁来定义 plan？会不会出现两套阶段门互相打架？ 辨析：会。两者在 Specification/Plan 环节重叠而非正交——这是原笔记忽略的隐含假设。 裁定 + 修订：原"二者关注点互补"的说法过于乐观。已在 5.2 改为"可落地但必须划清主流程归属"，并给出具体操作（OpenSpec 作唯一 SoT，Superpowers 仅在 Apply 阶段接管执行纪律，关闭其 brainstorming/writing-plans）。✅

#Q3｜反例："Superpowers 强制程度极强、不可跳过"——找得到反例吗？

诘问：笔记自己在 3.6 写了"用户显式指令可覆盖 skills"、"compliance is tested, not guaranteed"。那"不可跳过"还成立吗？ 辨析：不成立（作为绝对命题）。它只是很强的提示层约束，用户一句话就能覆盖，且压缩/长会话会削弱。 裁定 + 修订：已在第 0 章表格把"极强（不可跳过）"改为"强（HARD-GATE + hook；但提示层、用户指令可覆盖）"，3.6 加交叉引用。✅

#Q4｜定义一致性：Superpowers"无独立规格层"——但 design.md 不就是规格吗？

诘问：它明明把 docs/superpowers/specs/*-design.md commit 进仓库了，凭什么说"无规格层"？是不是自相矛盾？ 辨析：取决于"规格"的定义。按本体 A1，规范性规格须使"验证(产物, 规格)"可判定；Superpowers 的 design.md 是描述性设计文档，不含 delta spec 那种带 WHEN/THEN 场景的可执行需求，也不被 archive 回写为 SoT。 裁定 + 修订：不是矛盾，是定义粒度问题。已在第 0 章把该行明确为"一次性设计/计划文档（commit 入库，非规范性 spec）"，并在 1.5 映射表中统一措辞。✅

#Q5｜后果："三者都停留在流程/提示层而非沙箱"——这个结论能推出什么？

诘问：若真如此，Ouroboros 的 exec_sandbox（默认 true）、Superpowers 的 git worktree 又算什么？ 辨析：原结论把"逻辑约束"与"执行隔离"混为一谈。Ouroboros 确有可选执行沙箱、Superpowers 有 worktree 物理隔离，但它们都不是形式化验证的沙箱，本质仍是"提示/流程驱动 + 可选环境层隔离"。 裁定 + 修订：已在 5.3 风险 1 改为精确表述。✅

#Q6｜元问题："评估输出成为下一代 Seed 输入"与"Seed 不可变"矛盾吗？

诘问：既然 Seed 不可变，又怎么被下一代评估输出更新？ 辨析：不矛盾，但要区分实例级/类型级不可变（公理 A5）：单次执行冻结 Seed 实例，进化时生成新实例、旧实例留在 EventStore 里。 裁定 + 修订：已在 4.1 加"本体澄清"注释，并新增公理 A5。✅

#Q7｜证据来源："轻量"与"30+ 工具、12 workflow、stores beta"——名实相符吗？

诘问：称 OpenSpec"轻量"，却又列了大量工具/workflow/store，到底轻在哪？ 辨析："轻量"是相对 Spec Kit（Python、严格阶段门）而言的方法论轻（无固定门、可自由迭代、单 CLI），不是功能少。 裁定 + 修订：已在 1.6 与 5.2 把"轻量"限定在"接入成本/流程约束"维度，并保留"体系可大"的事实。✅

#8. 小结（takeaway）

  • 本体视角：三者是"意图→规格→任务→产物→证据→状态"这条链上的不同实现——OpenSpec 强在规格与状态，Superpowers 强在执行与证据，Ouroboros 覆盖全链路。
  • OpenSpec = 规格层：可变增量 spec + Git 审计，五步闭环，最适合存量项目与团队协作。
  • Superpowers = 方法论：15 个 skills + hooks 驱动 TDD 与子代理审查，代码质量纪律最强，但属提示层、可被用户覆盖。
  • Ouroboros = Agent OS：访谈冻结 Seed，委托外部 runtime 执行，三阶段评估 + 进化收敛，自动化最高也最重。
  • 组合需谨慎：OpenSpec + Superpowers 在 Spec/Plan 环节重叠，须划清主流程归属（见 5.2）；不要三套全装。
  • 三者核心都是流程/提示层约束（Ouroboros 另有可选执行沙箱），质量仍取决于模型能力与人的审查；选型看痛点是"规格不清"、"代码质量差"还是"想全自动交付"。
