#信令、SDP 与 ICE

WebRTC 规范里没有信令。它只规定了两个端点如何用一个叫 RTCPeerConnection 的对象协商媒体、建立加密通道，至于 SDP 和候选地址怎么交换，留给业务自己实现。在线教育里，这根「信令线」还额外承担了举手、上台、翻页、板书、上下课——所以它往往比媒体链路更容易出问题。

#1. 信令要传什么

  • 媒体协商与网络候选是 WebRTC 标准要求的。
  • 连接控制是工程实践：ICE 打不通时主动重启，而不是等 30s 超时。
  • 课堂业务是产品语义，必须有序、可回执、可拦截。

#3. SDP 解剖

SDP 是纯文本，按行组织，m= 段落描述一条媒体流：

1v=0
2o=- 4611731400430051336 2 IN IP4 127.0.0.1
3s=-
4t=0 0
5m=audio 9 UDP/TLS/RTP/SAVPF 111 63 9 0 8 13 110 126
6c=IN IP4 0.0.0.0
7a=mid:0
8a=sendrecv
9a=rtpmap:111 opus/48000/2
10a=fmtp:111 minptime=10;useinbandfec=1
11a=ice-ufrag:F7gI
12a=ice-pwd:x9cml/YzichV2+XlhiMu8g
13a=fingerprint:sha-256 6B:8B:F0:...:0E
14a=setup:actpass
15m=video 9 UDP/TLS/RTP/SAVPF 96 97 98
16a=mid:1
17a=sendonly
18a=rtpmap:96 VP8/90000
19a=rtcp-fb:96 nack
20a=rtcp-fb:96 nack pli
21a=rtcp-fb:96 transport-cc
22a=ssrc:1234 cname:abc
字段作用排查价值
m= 行媒体类型、端口、传输协议、载荷类型列表数量对不上说明轨道没加进去
a=sendrecv/sendonly/recvonly/inactive方向inactive 是最常见的「连上了但没流」
a=rtpmap编码与时钟频率双方无交集会导致协商失败
a=fmtp编码参数（如 Opus FEC）关掉 useinbandfec 会明显削弱弱网表现
a=rtcp-fb反馈机制（NACK、PLI、transport-cc）没有 transport-cc 就没有拥塞控制反馈
a=ice-ufrag / a=ice-pwdICE 认证复用错误会导致连通性检查全失败
a=fingerprintDTLS 证书指纹不匹配则媒体加密握手失败
a=setupDTLS 角色双方都是 active/passive 会卡住

SDP 不是配置，是协商结果。 改 SDP 前必须理解对端会怎么响应，直接「魔改」是线上事故的常见来源。

#4. ICE：把「能连上」变成「连得上」

ICE 的任务是找出两端之间可用的网络路径，流程分三步：

候选类型来源特点
host本机网卡地址同局域网最快
srflxSTUN 服务器反射出的公网地址能穿透大多数 NAT
relayTURN 服务器中继一定可用，但成本与延迟最高

工程要点：

  1. TURN 不是可选项。对称型 NAT、企业防火墙封 UDP 的场景，只有 relay 能救。
  2. Trickle ICE 能显著缩短首帧。不必等候选收集完再发 SDP。
  3. ICE restart ≠ 重新 joinRoom。网络切换（Wi-Fi → 4G）应优先 ICE restart；只有信令会话也断了才需要重新进房。
  4. mDNS 候选在部分浏览器默认开启（xxx.local），跨网段无法解析，表现为「本地能连、跨网连不上」。

#5. DTLS-SRTP：媒体为什么是加密的

  • 握手用 DTLS 1.2/1.3，证书是自签名的，靠 SDP 里的 a=fingerprint 校验。
  • 媒体用 SRTP 加密，控制包用 SRTCP。
  • 指纹不匹配的典型表现是 ICE 成功、DTLS 失败、永远没有首帧。
  • 企业内网做 TLS 中间盒时，可能破坏 DTLS，需要放行 UDP。

#6. 信令通道的工程化

#6.1 为什么是 WebSocket

方案延迟双向有序结论
HTTP 轮询高否单次内有序仅作兜底
SSE中单向是只适合下行通知
WebSocket低是是课堂信令的标准选择
DataChannel低是可配依赖已建连，不能用于建连本身

项目同时维护两条 WS：roomServer（课堂控制）与 chatServer（聊天，独立重连与限流），互不拖累。

#6.2 请求-响应要能对上号

1type SignalMessage = {
2    jsonrpc: '2.0';
3    id: string;        // 请求关联 id
4    method: string;    // 业务方法
5    params?: unknown;
6    roomID?: string;
7};

工程约定：

  • 5s 超时：没有回包就报 MESSAGE_TIMEOUT，避免 Promise 永挂。
  • 幂等：超时重试必须保证重复执行无副作用，例如「开始上课」重发不应重复扣课时。
  • 分流：带 to 的是点播（点对点），带 method 的是广播/通知。两者混在一个通道里，必须靠结构区分而不是靠猜。
  • 过滤：currentRoomID 与本地不一致的消息要丢弃，否则切班期间会串班。

#6.3 心跳与重连

项目里 ping 每 10s 一次，连续 3 次无响应判定超时；onClose / onError 走 1–6s 随机重连，避免服务端故障恢复瞬间被全部客户端打垮。随机退避比固定间隔重要，这是雪崩防护。

#6.4 重连后必须做状态重建

重连成功不等于状态正确：断线期间可能有人上台、有人下课、课件翻页、老师被踢。所以重连后要拉全量：

查询恢复的状态
queryActiveUsers台上用户、自己的上下台状态
queryUsers在线名单、角色
queryClass上课状态、开始时间
queryDocs课件列表与当前页
queryDisableRaiseHand / queryNotices课堂管控与公告

增量重放不可行——服务端不一定保留完整历史，顺序也无法保证。全量覆盖 + 幂等处理才是正确做法。

#7. 项目落地：三层信令模型

层职责关键点
Sender语义化 API：query / broadcast / unicast / customData关心响应与不关心响应要分开
RoomServer消息分流、拦截、回放切班窗口会拦截非白名单消息
V5Websocket连接、心跳、超时、重连与 RTC 重连解耦
Handlermethod → VM 方法未知 method 静默丢弃，新增信令必须同步加路由

两个易错点：

  1. 未知 method 不报错。忘记注册 handler 的表现是「功能静默失效」，排查时先确认路由表。
  2. 切班期间的信令拦截。只放行 toggleClass 与匹配 id 的广播，其余入队；如果广播的 id 与 toggleClass 不一致，会被永久丢弃，表现为「切班后黑屏」。

#8. 信令与媒体的重连要分开处理

故障现象正确处理
WS 断开收不到任何课堂事件WS 重连 + 拉全量状态
ICE 断开信令正常、媒体中断ICE restart；失败再重建 RTC
页面长时间后台心跳被节流、媒体冻结监听 visibilitychange，回前台重建
服务端主动踢人收到 rejoin 类消息不重连，直接退出并提示

把三者混成一个「重连」逻辑，是弱网体验差的常见根因：媒体抖一下就重进房，学生要重新等 3 秒首帧。
