#WebRTC 与实时互动课堂：专栏导读

一套面向「在线教育直播间」的 WebRTC 知识地图。既不满足于「会调 SDK」，也不陷入协议细节无法落地——每一章都对应到真实项目里的模块与故障场景。

#这个专栏解决什么问题

在线教育直播间的本质，是把四类实时数据可靠地送到对的人手里：

数据类型典型载体要求
音视频媒体RTC（WebRTC / 火山 VE / 腾讯 TRTC）低延迟、抗弱网、可分层
课堂控制信令WebSocket有序、可回执、可拦截
板书与课件操作WebSocket（形状信号）可重放、可缓存、可断线恢复
业务状态HTTP + 信令最终一致、可补偿

只懂其中之一，就会在排障时迷失：明明是「学生看不到老师」，可能是采集没开、可能是发布成功但订阅没做、可能是自动播放被浏览器拦截，也可能是 ICE 没打通。本专栏按「采集 → 信令 → 拓扑 → 课堂链路 → 弱网 → 排障」的顺序拆开这条链。

#与技术栈的关系

本专栏以两套体系对照讲解：

  • 标准 WebRTC：getUserMedia / RTCPeerConnection / SDP / ICE / DTLS-SRTP，是所有 RTC 的公共底座。
  • 本项目实践：@v5-live/core 通过 rtcAdapter 抽象了火山引擎 VE 与腾讯 TRTC 两套云端 SDK，业务侧只与 LiveRoom 和 13 个 ViewModel 交互。

关键边界：SDK 只负责媒体与画布，不负责课堂语义。谁上台、谁能说话、课件翻到第几页，全部由信令层定义。

章节解决的核心问题对应项目模块

#十个必须先建立的概念

概念一句话解释常见误区
信令（Signaling）交换 SDP 与候选地址的业务通道，WebRTC 本身不规定以为 RTCPeerConnection 会自动找到对方
SDP媒体能力与网络参数的文本描述以为 SDP 是「配置」而非「协商结果」
ICE用 STUN/TURN 找出双方可达路径的过程认为有公网 IP 就不需要 TURN
DTLS-SRTP媒体加密：DTLS 握手协商密钥，SRTP 加密传输把它和 HTTPS 证书体系混为一谈
SFU每个端只上行一路，由服务器转发多路以为大班课堂是「老师直连所有学生」
发布/订阅先 publish 自己的流，再由别人 subscribe以为发布了对方就一定会收到
Simulcast / SVC同一路视频编出多个质量层，按需下发把它和「多路摄像头」混为一谈
3AAEC 回声消除、ANS 降噪、AGC 自动增益以为开了 3A 就一定没有回声
自动播放策略无用户手势时浏览器可能拒绝播放/挂起音频只处理 video.play() 的 Promise
SEI随视频帧下发的带内自定义数据用文本消息传时间戳导致音画不同步

#本项目的技术取舍

为什么同时接火山 VE 和腾讯 TRTC：房间配置里的 rtcConfig.rtcVendor 决定引擎（VOLCANO=2 / TENCENT=3），迁云、容灾、地域合规都可以按房间灰度，而不改业务代码。

为什么白板不走 DataChannel：板书信号需要服务端缓存、跨端重放、断线恢复和权限校验，DataChannel 是端到端的，天然做不到；项目里笔迹走 WebSocket 广播（operateShape / operatePen），白板包只负责画、不负责传。

为什么宿主把 isAutoSubscribe 设为 false：大班课堂同时可能有几十路流，全量订阅会把下行带宽打满。宿主按「台上用户 + 当前可见画面」显式订阅，把带宽花在看得见的地方。

#自检清单

读完这个专栏，你应该能回答：

  • 学生反馈「听不到老师」，如何按「采集 → 发布 → 订阅 → 播放 → 渲染」五层定位？
  • 为什么 ICE 连接成功但视频一直黑屏？先看哪些 getStats 字段？
  • 教室网络抖动到 20% 丢包时，音频和视频分别靠什么机制保命？
  • 断线重连后，为什么要拉一次全量状态而不是重放增量信令？
  • 大班 1 对 100 的课堂，服务器出口带宽怎么估算？
