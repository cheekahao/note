#STAR 案例模板

面试中最容易被追问的是「你具体做了什么」。每个案例都要有：背景、目标、动作、结果、复盘。

#案例一：启动优化

1S（背景）：桌面客户端冷启动约 2.4s，用户反馈打开慢，首屏白屏明显。
2T（目标）：把 P95 冷启动降到 1.2s 以内，首屏白屏 < 300ms。
3A（动作）：
4  1. 建立埋点：主进程 module-loaded / app-ready / window-created、
5     渲染进程 FCP / LCP / TTI，按版本与平台上报。
6  2. 画瀑布图，发现主进程同步读取配置与全量加载 SDK 占 600ms，
7     渲染层首屏 bundle 过大占 700ms。
8  3. 主进程：配置改异步、SDK 延迟加载、启用编译缓存。
9  4. 渲染层：路由懒加载、首屏骨架、移除首屏未使用组件。
10  5. 窗口：show:false + ready-to-show + 背景色。
11R（结果）：P95 从 2.4s 降到 1.1s，白屏从 800ms 降到 220ms，
12  并通过 CI 启动门禁防止反弹。
13复盘：首次启动与热启动差异大，后续补齐首次安装场景的基线。

讲述要点：

  • 一定要有「怎么测」和「怎么归因」，否则会被认为只是执行了优化清单。
  • 结果用分位数，不用平均值。
  • 说明如何防止回归。

#案例二：内存治理

1S：应用长时间运行后内存从 220MB 涨到 600MB，切换页面越来越卡。
2T：定位泄漏并建立内存预算与门禁。
3A：
4  1. 用 app.getAppMetrics 分进程采样，确认增长来自渲染进程。
5  2. DevTools Memory 抓取操作前后的堆快照，对比发现
6     Detached HTMLElement 与 EventListener 持续增长。
7  3. 定位到某页面组件卸载时未移除 window 监听与定时器。
8  4. 统一封装 usePageLifecycle，强制清理监听、定时器、IPC 订阅。
9  5. 对缓存加 LRU 上限，图片按显示尺寸加载。
10  6. CI 增加 20 次页面切换的内存增量门禁。
11R：常驻内存稳定在 280MB 左右，长时运行不再持续上涨。

追问准备：

  • 如何区分缓存与泄漏？
  • 为什么用堆快照而不是只看进程内存？
  • GPU 内存怎么观察？

#案例三：崩溃率治理

1S：某版本崩溃率上升到 0.8%，主要集中在 Windows 部分机型。
2T：把崩溃率降到 0.1% 以下，并建立可持续的监控体系。
3A：
4  1. 接入 crashReporter，收集 minidump、版本、平台、操作路径。
5  2. 建立符号归档：原生模块 PDB/dSYM + Electron symbols。
6  3. 聚合堆栈，发现集中在某个原生模块的 GPU 相关调用。
7  4. 与模块维护方定位为驱动兼容问题，增加降级与重试。
8  5. 补充 render-process-gone 的恢复策略与重试上限。
9  6. 发布灰度，崩溃率超阈值自动停止放量。
10R：崩溃率降到 0.08%，并有版本级看板与告警。

#案例四：包体积与增量更新

1S：安装包 210MB，增量更新经常接近全量，用户升级成本高。
2T：安装包降到 150MB 以内，增量包平均 < 15MB。
3A：
4  1. 分析 app.asar 与 unpacked 目录，发现重复图片、未使用字体、
5     测试依赖被打入生产包。
6  2. files 白名单 + 依赖裁剪 + 图片压缩 + 字体子集化。
7  3. 原生模块只保留目标架构，移除多余 locales。
8  4. 接入 blockmap 差量更新，调整资源打包粒度。
9  5. CI 增加体积门禁与差异报告。
10R：安装包 148MB，增量包平均 9MB，升级成功率提升。

#高频面试题与答题框架

#1. Electron 的进程模型是怎样的？

答题结构：

  1. 主进程：Node 环境、窗口与生命周期、系统能力。
  2. 渲染进程：Chromium、页面、沙箱。
  3. GPU 进程：光栅化与合成。
  4. Utility 进程：网络服务、Node 子任务。
  5. 与 Chrome 的对应关系。
  6. 性能含义：主进程单点阻塞、渲染进程隔离、进程间序列化成本。

#2. 为什么不能开nodeIntegration？

  • XSS 会升级为任意代码执行。
  • 渲染进程可能加载远程/第三方内容，信任边界不可控。
  • 正确做法：contextIsolation + sandbox + preload 白名单 + IPC 校验。

#3. IPC 怎么设计才安全又高效？

安全：

  • 只暴露具名方法，不暴露 ipcRenderer。
  • 参数校验、来源校验、路径限制。
  • 不加载不可信内容。

高效：

  • 请求响应优先 invoke/handle。
  • 高频事件按帧合并。
  • 大对象传 ID/路径，二进制用 MessagePort。
  • 禁止 sendSync，主进程不做重活。

#4. 启动优化怎么做？

按「测量 → 拆解 → 优化 → 门禁」回答：

  1. 定义冷/热启动、首屏、TTI。
  2. 主进程、窗口、渲染进程三段埋点。
  3. 用 tracing 找最大耗时段。
  4. 主进程延迟加载、异步 IO、编译缓存。
  5. 渲染层代码分割、骨架屏、资源预加载。
  6. 窗口 ready-to-show、背景色、复用。
  7. CI 门禁与看板。

#5. 内存泄漏怎么排查？

  1. 分进程采样，确认增长源。
  2. GC 后仍上涨才判定泄漏。
  3. 堆快照对比，按 Delta 排序。
  4. 回溯引用链，定位持有者。
  5. 常见模式：监听、定时器、全局缓存、Detached DOM、MessagePort。
  6. 修复后用同样场景回归并加门禁。

#6. 主进程阻塞会怎样？如何避免？

  • 所有窗口的 IPC、菜单、窗口操作都会被阻塞。
  • 渲染进程等待主进程返回，表现为界面卡顿。
  • 避免：异步 IO、重任务移到 utilityProcess、限制并发、超时、禁止同步 IPC。

#7. 崩溃监控怎么落地？

  • crashReporter 采集 minidump。
  • 符号表归档与符号化。
  • 聚合、去重、按版本/平台统计。
  • 渲染进程 render-process-gone 单独上报。
  • JS 异常通过 uncaughtException / unhandledRejection / window.onerror。
  • 灰度与自动止损。

#8. 包体积怎么优化？

  • 分析 asar 与 unpacked 目录。
  • 依赖裁剪、files 白名单。
  • 图片/字体/语言包精简。
  • 原生模块按架构拆分。
  • 压缩与去 sourcemap。
  • 增量更新用 blockmap。

#9. asar 是什么？什么需要解包？

  • 单文件归档，减少文件数、加快读取。
  • 需要真实路径的内容要解包：.node、外部可执行文件、部分资源。
  • 解包过多会增加体积与安装成本。

#10. Native Addon 的 ABI 问题怎么解决？

  • Node-API 提供稳定 ABI，但 Electron 场景仍建议 rebuild。
  • @electron/rebuild / electron-builder install-app-deps。
  • 预编译二进制要匹配 Electron ABI 与架构。
  • 排查 NODE_MODULE_VERSION、dlopen、DLL 缺失。

#11. 如何制定渲染性能标准？

  • 指标：FPS、长任务、INP、LCP、掉帧率。
  • 目标：滚动 ≥ 55fps、关键路径无 > 100ms 长任务。
  • 场景：长列表、大图、动画、多窗口。
  • 落地：组件规范、评审清单、CI 场景、发布验收。

#12. 你如何从架构层面解决性能问题？

  • 预算：启动、内存、渲染、体积。
  • 平台化：虚拟列表、图片缓存、IPC SDK、监控 SDK。
  • 门禁：CI 阻断劣化。
  • 观测：看板、告警、复盘。
  • 组织：规范、评审、培训。

#设计启动监控

要点：

  • 主进程 performance.now() 打点。
  • 渲染进程 Navigation/Paint/LCP/LongTask。

#排查白屏

  1. DevTools Console 是否有报错。
  2. Network 是否资源 404/CSP 拦截。
  3. loadFile/loadURL 路径是否正确。
  4. 渲染入口是否构建成功。
  5. preload 是否抛错导致页面脚本未执行。
  6. GPU/驱动问题（尝试诊断参数，不作为生产方案）。
  7. 打包产物中 app.asar 是否包含资源。

#写一个限流/并发控制

1export function createLimiter(max: number) {
2  let active = 0;
3  const queue: Array<() => void> = [];
4
5  const next = (): void => {
6    if (active >= max) return;
7    const run = queue.shift();
8    if (run) {
9      active += 1;
10      run();
11    }
12  };
13
14  return function limit<T>(task: () => Promise<T>): Promise<T> {
15    return new Promise<T>((resolve, reject) => {
16      queue.push(() => {
17        task()
18          .then(resolve, reject)
19          .finally(() => {
20            active -= 1;
21            next();
22          });
23      });
24      next();
25    });
26  };
27}
