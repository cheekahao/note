#IPC 通信体系

#本章目标

  • 掌握 Electron 的三种 IPC 模式：单向消息、请求响应、双向流。
  • 设计类型安全、权限可控的 IPC 接口，而不是到处裸写通道字符串。
  • 理解 IPC 的性能成本，避免同步通信、高频小消息与大对象复制。
  • 能定位「通道没反应」「preload 没生效」「主进程卡住」等常见问题。

#IPC 全景

三个角色：

角色可用模块职责
渲染进程无 Node、无 ipcRenderer只调用 preload 暴露的白名单 API
preloadipcRenderer、contextBridge定义通道、参数校验、暴露 API
主进程ipcMain、完整 Node处理请求、访问系统能力、返回结果

#三种通信模式

#1. 请求响应：invoke /handle

最常用，语义接近函数调用。

1// preload.ts
2import { contextBridge, ipcRenderer } from 'electron';
3
4contextBridge.exposeInMainWorld('api', {
5  readConfig: () => ipcRenderer.invoke('config:read'),
6});
1// main.ts
2import { ipcMain } from 'electron';
3
4ipcMain.handle('config:read', async () => {
5  return { theme: 'dark', language: 'zh-CN' };
6});
1// renderer.js
2const config = await window.api.readConfig();

特点：

  • 返回 Promise，主进程抛出的错误会以 reject 形式传回。
  • 每个通道只能注册一个 handle，重复注册会抛错。
  • 返回值必须可结构化克隆（不能传函数、Symbol、DOM 节点）。

#2. 单向消息：send /on

只通知，不等待结果。

1// preload.ts
2contextBridge.exposeInMainWorld('api', {
3  track: (event: string, payload: Record<string, unknown>) => {
4    ipcRenderer.send('telemetry:track', { event, payload });
5  },
6});
1// main.ts
2ipcMain.on('telemetry:track', (_event, data) => {
3  logger.info('telemetry', data);
4});

适合埋点、日志、状态同步。缺点是失败无反馈，重要操作不要只用单向消息。

#3. 双向流：MessageChannelMain

适合持续、高频、大流量的数据通道，例如实时日志、音视频帧、协作编辑。

1// main.ts
2import { BrowserWindow, MessageChannelMain } from 'electron';
3
4function connectStream(win: BrowserWindow): void {
5  const { port1, port2 } = new MessageChannelMain();
6
7  port1.on('message', (event) => {
8    console.log('main received', event.data);
9  });
10  port1.start();
11
12  win.webContents.postMessage('stream:port', null, [port2]);
13}
1// preload.ts
2import { contextBridge, ipcRenderer } from 'electron';
3
4ipcRenderer.on('stream:port', (event) => {
5  const [port] = event.ports;
6  port.onmessage = (e) => {
7    // 处理流数据
8    window.dispatchEvent(new CustomEvent('stream-data', { detail: e.data }));
9  };
10  port.start();
11});

和 invoke 相比，MessagePort 的优势：

  • 建立一次，后续消息不再经过主进程的 ipcMain 路由。
  • 可以传递 ArrayBuffer 等可转移对象，减少复制。
  • 适合双向、持续通信。

代价是生命周期要自己管理，端口忘记关闭会造成泄漏。

#类型安全 IPC 设计

裸写通道字符串的问题：拼写错误、参数类型不一致、重构后遗漏。用一个共享类型文件约束两端。

1// src/shared/ipc.ts
2export interface IpcApi {
3  'app:ping': {
4    request: void;
5    response: string;
6  };
7  'file:readText': {
8    request: { path: string };
9    response: { content: string };
10  };
11  'window:minimize': {
12    request: void;
13    response: void;
14  };
15}
16
17export type IpcChannel = keyof IpcApi;
18export type IpcRequest<C extends IpcChannel> = IpcApi[C]['request'];
19export type IpcResponse<C extends IpcChannel> = IpcApi[C]['response'];

主进程统一注册：

1// src/main/ipc/registry.ts
2import { ipcMain, IpcMainInvokeEvent } from 'electron';
3import type { IpcChannel, IpcRequest, IpcResponse } from '../../shared/ipc';
4
5type Handler<C extends IpcChannel> = (
6  event: IpcMainInvokeEvent,
7  payload: IpcRequest<C>,
8) => IpcResponse<C> | Promise<IpcResponse<C>>;
9
10export function handle<C extends IpcChannel>(channel: C, handler: Handler<C>): void {
11  ipcMain.handle(channel, (event, payload) => handler(event, payload));
12}
1// src/main/ipc/file.ts
2import { handle } from './registry';
3import fs from 'node:fs/promises';
4
5handle('file:readText', async (_event, { path }) => {
6  const content = await fs.readFile(path, 'utf-8');
7  return { content };
8});

preload 统一暴露：

1// src/preload/index.ts
2import { contextBridge, ipcRenderer } from 'electron';
3import type { IpcChannel, IpcRequest, IpcResponse } from '../shared/ipc';
4
5const api = {
6  invoke<C extends IpcChannel>(
7    channel: C,
8    payload: IpcRequest<C>,
9  ): Promise<IpcResponse<C>> {
10    return ipcRenderer.invoke(channel, payload);
11  },
12};
13
14contextBridge.exposeInMainWorld('api', api);

渲染进程类型声明：

1// src/renderer/global.d.ts
2import type { IpcChannel, IpcRequest, IpcResponse } from '../shared/ipc';
3
4declare global {
5  interface Window {
6    api: {
7      invoke<C extends IpcChannel>(
8        channel: C,
9        payload: IpcRequest<C>,
10      ): Promise<IpcResponse<C>>;
11    };
12  }
13}
14
15export {};

这里有一个安全权衡：直接把 invoke 暴露给页面，页面可以调用任意已注册通道。更严格的做法是按业务暴露具名方法：

1contextBridge.exposeInMainWorld('api', {
2  ping: () => ipcRenderer.invoke('app:ping'),
3  readText: (path: string) => ipcRenderer.invoke('file:readText', { path }),
4});

具名方法更安全，也更容易做参数校验。类型安全与最小暴露面可以结合：共享类型约束内部实现，preload 只暴露业务需要的方法。

#参数校验与权限

渲染进程传来的任何参数都不可信，尤其是文件路径、URL、命令。

1import path from 'node:path';
2import fs from 'node:fs/promises';
3import { app, ipcMain } from 'electron';
4
5const workspaceRoot = path.join(app.getPath('documents'), 'MyApp');
6
7ipcMain.handle('file:readText', async (_event, payload: { path: string }) => {
8  const target = path.resolve(workspaceRoot, payload.path);
9  const relative = path.relative(workspaceRoot, target);
10
11  // 防止 ../ 路径穿越
12  if (relative.startsWith('..') || path.isAbsolute(relative)) {
13    throw new Error('forbidden path');
14  }
15
16  return { content: await fs.readFile(target, 'utf-8') };
17});

更严格的做法是只接受「资源 ID」，由主进程映射到真实路径，页面永远拿不到任意文件访问能力。

同时应校验消息来源：

1ipcMain.handle('app:ping', (event) => {
2  const url = event.senderFrame?.url ?? '';
3  if (!url.startsWith('file://') && !url.startsWith('https://app.example.com')) {
4    throw new Error('untrusted sender');
5  }
6  return 'pong';
7});

event.senderFrame 在 Electron 新版本中可能为 null（frame 已销毁），需要判空。

#IPC 的性能成本

一次 invoke 的链路大致是：

成本来源：

成本说明优化
序列化/反序列化结构化克隆，大对象成本高传路径/ID，分批，ArrayBuffer
进程切换跨进程调度合并请求，减少往返次数
主进程排队主进程单线程不在主进程做重活
同步等待sendSync 阻塞渲染禁止使用

#避免同步 IPC

1// 不要这样做：同步等待主进程，界面直接冻结
2const result = ipcRenderer.sendSync('config:read');

sendSync 会阻塞渲染进程，直到主进程返回。主进程一旦忙，界面就卡死。新代码中应完全避免。

#高频消息合并

鼠标移动、滚动、窗口 resize 这类高频事件，不要每次都发 IPC。

1// renderer.ts
2let pending: Array<{ x: number; y: number }> = [];
3let scheduled = false;
4
5window.addEventListener('pointermove', (e) => {
6  pending.push({ x: e.clientX, y: e.clientY });
7
8  if (!scheduled) {
9    scheduled = true;
10    requestAnimationFrame(() => {
11      window.api.invoke('pointer:batch', pending);
12      pending = [];
13      scheduled = false;
14    });
15  }
16});

按帧合并后，每秒最多 60 次，而不是数百次。

#大对象传输

1// 不推荐：每次都传完整大数组
2await window.api.invoke('table:update', rows);
3
4// 推荐：分页或只传变更
5await window.api.invoke('table:patch', { start, changes });

如果要传二进制数据，使用 ArrayBuffer 或 MessagePort，避免 JSON 化。

#主进程阻塞的连锁反应

主进程是 IPC 的中心。一旦主进程执行同步耗时任务，所有渲染进程的 invoke 都会排队：

1// 错误示例：主进程同步读大文件
2ipcMain.handle('report:load', () => {
3  const raw = fs.readFileSync('/data/huge-report.json', 'utf-8');
4  return JSON.parse(raw);
5});

用户感知是「点了按钮没反应，窗口也拖不动」。正确做法：

1ipcMain.handle('report:load', async () => {
2  const raw = await fs.readFile('/data/huge-report.json', 'utf-8');
3  return JSON.parse(raw);
4});

如果解析本身就很重，应放到 utilityProcess：

1ipcMain.handle('report:load', async () => {
2  return parseInUtilityProcess('/data/huge-report.json');
3});

#常见问题排查

#window.api is undefined

  1. preload 路径是否指向编译后的 .js。
  2. contextIsolation 是否为 true（推荐）且使用了 contextBridge。
  3. preload 是否抛错，查看主进程终端输出。
  4. 页面是否在 DOM 加载前就访问了 API。

#No handler registered for 'xxx'

通道名拼写不一致，或 ipcMain.handle 在窗口加载后才注册。建议在 app.whenReady() 中统一注册，再创建窗口。

#An object could not be cloned

返回值包含函数、Promise、DOM 节点、类实例。只返回纯数据，错误用 throw new Error()。

#错误信息被包装

invoke 抛出的错误在渲染进程看到的是 Error invoking remote method 'xxx': ...，原始错误在 message 中。可以在 preload 统一转换：

1async function safeInvoke<T>(channel: string, payload?: unknown): Promise<T> {
2  try {
3    return await ipcRenderer.invoke(channel, payload);
4  } catch (err) {
5    const message = err instanceof Error ? err.message : String(err);
6    throw new Error(message.replace(/^Error invoking remote method '[^']+':\s*/, ''));
7  }
8}

#通道泄露与重复注册

热重载或多次初始化时，ipcMain.handle 重复注册会抛错。把注册逻辑放在模块顶层并保证只执行一次，或在注册前 ipcMain.removeHandler(channel)。

#IPC 设计规范

一份可以直接落到团队规范里的清单：

  1. 通道命名采用 domain:action，例如 file:readText、window:minimize。
  2. 所有通道在 shared/ipc.ts 中声明请求/响应类型。
  3. 渲染进程只能通过 preload 暴露的方法访问 IPC，禁止暴露 ipcRenderer 本身。
  4. 主进程对参数做校验，文件路径必须限制在工作目录内。
  5. 禁止 sendSync；高频事件按帧或按时间窗口合并。
  6. 大对象传 ID/路径，二进制走 MessagePort/ArrayBuffer。
  7. 每个 handle 都要有错误处理与超时策略。
  8. 不在主进程做超过几十毫秒的同步计算。

#本章小结

  • 三种 IPC 模式分别对应通知、请求响应、持续流，按场景选择。
  • contextBridge 是唯一推荐的桥接方式，暴露面越小越安全。
  • 类型安全的 IPC 需要共享类型、统一注册、统一错误转换。
  • IPC 的性能瓶颈主要来自序列化、进程切换与主进程阻塞。
  • 参数校验与来源校验是 IPC 的安全底线。
